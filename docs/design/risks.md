- **`isAuthorizedPartial` is experimental and its residual shape is unversioned.** Cedar ships no formal proofs for partial evaluation and the team expects API changes; the recommended successor (TPE, RFC 95) is NOT compiled into the WASM build (only the `partial-eval` feature is). Mitigation: pin `@cedar-policy/cedar-wasm` to an exact version (4.12.0) during alpha; the vendored Cedar corpus + property-based soundness suite run on every dependency bump and are the tripwire; `check()` never depends on partial eval, so a regression degrades query filtering only, never enforcement.
- **An unsound query-plan compiler silently returns wrong rows — the top security risk in the package.** Mitigations, in order of strength: (1) `unsupportedResidual: 'error'` is the DEFAULT, so anything untranslatable throws; (2) `approximation.ts` derives the widening direction from `(effect, polarity)` as one tested function rather than ad-hoc branches; (3) the property-based test asserts *set equality* between the plan and brute-force `check()` over random policies and populations; (4) `evaluatePlanNode` ships publicly so the ORM drivers differential-test their SQL against the same oracle.
- **An errored Cedar policy silently stops forbidding.** Verified live: a policy that errors gets a `{"Value":false}` residual and an entry in `errored[]`, so an errored `forbid` disappears from the plan. Mitigation: `plan()` throws `ErroredPolicyError` by default when `errored[]` is non-empty; the typed `entity()` builder rejects attributes absent from the vocabulary so the common cause (missing attribute) fails at construction; `validateOnLoad` runs Cedar `validate()` at preparse time and refuses to cache a policy set with validation errors.
- **Query-plan latency: `isAuthorizedPartial` measured at 2.28 ms/op and cannot use the preparse cache** (`PartialAuthorizationCall` has no `preparsedPolicySetId` field) — ~17x a stateful check. Mitigation: mandatory plan LRU+TTL keyed on policy-set version + principal + action + context hash; `stats()` exposes hit rate so a low-hit-rate deployment is visible rather than mysteriously slow. Residual risk: high-cardinality context (e.g. a timestamp in context) destroys the cache key — documented, with guidance to keep planning contexts coarse.
- **WASM preparse memory is monotonic and there is no unregister API.** Measured: 2000 distinct policy-set ids = +126 MB RSS. Mitigation: ids are stable per tenant and never version-suffixed; invalidation re-preparses the SAME id (measured to free); LRU eviction overwrites with an empty policy set (measured to free and allow reuse). Residual risk: WebAssembly linear memory never returns pages to the OS, so peak RSS is sticky — must be stated in the README with a `maxScopes` sizing table.
- **Vocabulary builder type-level complexity.** `ResourceTypeFor<V, A>` narrowing resources per action is the kind of conditional type that produces unreadable errors and slow `tsc`. Mitigation: `expectTypeOf` tests pinning the exact inferred unions; a documented escape hatch (`engine.checkUnsafe(...)` taking plain strings) so a type-inference failure never blocks a consumer; the builder is testable independent of Cedar.
- **Nested-attribute residuals are the most natural way to write policies and are not pushdown-able** (`resource.owner.dept == 'eng'` needs a join). Left unaddressed, users hit `UnsupportedResidualError` constantly and conclude the feature is broken. Mitigation: README documents the flattening idiom (denormalise into a resource attribute) with worked examples; the error message names the exact sub-expression and suggests the flattening; the ORM driver packages own an optional declared-join mapping in a later milestone.
- **Bundling would break the WASM loader** — `nodejs/cedar_wasm.js` uses `__dirname` and `require('fs')`. Mitigation: `deps.neverBundle: [/^@cedar-policy\//]` in `tsdown.config.ts`, plus a CI smoke step that imports the built `dist/index.mjs` from a scratch ESM project on Node 22 and 24 and runs one real `check()`.
- `isAuthorizedPartial` is experimental and unproven (Cedar's own team ships no correctness proofs; the recommended successor TPE is NOT in the WASM build). Mitigation: pin `@cedar-policy/cedar-wasm` peer to `^4.9.1`; probe `typeof isAuthorizedPartial === 'function'` at engine construction and refuse to boot if `queryPlan` features are used without it; `queryPlan.fallback` defaults to `'deny'` (never silently widen); a dedicated non-blocking `canary` CI job runs the suite against `cedar-wasm@latest` so a breaking change surfaces the day it ships.
- Two physical copies of `@nestm/permissions-core` in node_modules = two WASM instances = `preparsePolicySet` IDs registered in one are invisible to the other, producing sporadic 'unknown policy set' errors. Mitigation: changesets `fixed` versioning across all four packages so a single range always resolves to one copy; core registers a `Symbol.for('@nestm/permissions-core/instance')` on `globalThis` and logs an error on duplicate load; the ORM drivers import only types + a pure AST walker and must never instantiate WASM (core's cedar import is lazy).
- The guard runs before pipes, so `:organizationId` arrives unvalidated and untyped — the exact hazard station handles by hand at `apps/api/src/authorization/permission.guard.ts:116-127`. Mitigation: `ResourceRef{kind:'param'}` carries a mandatory-by-convention `parseAs` codec (a Standard Schema, so a Zod branded schema drops straight in); no codec = the raw string is used as the Cedar entity id, which is documented as a deliberate, logged-once footgun.
- `PATH_METADATA` for the route audit comes from `@nestjs/common/constants`, a deep import into Nest internals that no SemVer promise covers. Mitigation: try/catch around the deep import with a `'path'` string-literal fallback, plus a unit test that asserts a known controller method is detected (fails loudly if Nest renames the key).
- Fail-open on an unloaded policy set would silently authorize everything during a store outage or a slow `OnModuleInit`. Mitigation: `PolicySetManager` is an explicit `'unloaded' | 'ready' | 'stale'` state machine; the guard calls `assertReady()` before anything else and throws `ServiceUnavailableException`; an e2e test boots with a deliberately failing store and asserts 503 on every guarded route.
- Cedar requires the full entity graph (principal + resource + all ancestors) per request, which is an N+1 database cliff hiding behind a clean API — station currently does a fresh transaction per org and is already N+1 by design (`tenancy.service.ts:70-84`). Mitigation: `EntityProviderRegistry` batches contributions per request and dedupes by `EntityUid`; `hooks.onDecision` carries entity-load counts and elapsed time so the cost is observable from day one; README documents caching as the integrator's responsibility with a worked example.
- `@RequirePermission` type safety depends on the app augmenting `PermissionsTypeRegistry`; unaugmented, actions degrade to `string` and every typo compiles — a silent loss of the library's main safety claim. Mitigation: `tests/unit/type-assertions.ts` covers both branches with `expectTypeOf`; the README quick start puts the `declare module` block in step 2, before the first decorator usage.
- NestJS 12 is supported through stable `^12.0.0` peer ranges. A non-blocking `@nestjs/*@next` canary remains the early-warning path for the next major line.
- **`isAuthorizedPartial` is experimental and has no `preparsedPolicySetId`.** Every driver behaviour depends on residual shapes that a Cedar patch release could change (core pins 4.12.0 exactly). Mitigation: the differential property suite in each driver is the tripwire; the non-blocking `canary` CI job bumps `@cedar-policy/cedar-wasm` nightly so a shape change surfaces as a red canary, not a production over-share. Fallback if partial eval regresses: `plan()` returns `CONDITIONAL` with `condition: {op:'true'}` plus a mandatory `postFilter` — correct but O(n) and pagination-breaking, so it must be gated behind an explicit opt-in flag, never a silent default.
- **An uncompilable node silently becoming `TRUE` is the CVE in this design.** Mitigated structurally: `planToSql`/`planToBrackets` are total functions returning a boolean expression (never `undefined`), drizzle's `and()/or()` `SQL | undefined` return is never surfaced, every unmapped attribute/hierarchy throws a typed error, and a property test asserts no input produces an absent WHERE clause. `ALWAYS_DENY` compiles to a literal `FALSE`, never to a skipped predicate.
- **LIKE-pattern escaping mismatch between Cedar and SQL.** Cedar `like` is case-sensitive over code points; Postgres `LIKE` on a `citext`/ICU-nondeterministic column is not, which silently over-matches. Mitigation: the compiler throws when `mapping.text.collation === 'case-insensitive'`, the escape character is bound as a parameter (`LIKE $1 ESCAPE $2`), and a fuzz suite compares Cedar's own decision against Postgres for random strings containing `%`, `_`, `\`, `*`. Needs a live test to confirm Postgres accepts a bound parameter in the `ESCAPE` position across the supported versions.
- **`permission_scope_versions` cannot be RLS-protected without breaking cache invalidation** (the poller runs with no organization context). The recommended carve-out — no RLS on a table holding only `(organization_id, counter)` — weakens station's 'every org-scoped table is RLS-forced' invariant and must be explicitly signed off in ADR-0019 and SECURITY.md. Alternative if rejected: an 'organization context unset' SELECT-only policy mirroring the identity lens, which leaks the set of org ids to the app role (already known to it), at the cost of a second exception to the mutual-exclusion rule.
- **Projection drift between `role_grants` and `permission_policy_links`.** They are written in the same Postgres transaction so there is no distributed-write problem, but an out-of-band `DELETE` (ops, a future migration, a cascade path we missed) would leave stale links that still grant access. Mitigation: a composite FK from `permission_policy_links(organization_id, link_id)` to `role_grants(organization_id, id)` with `ON DELETE CASCADE` makes drift structurally impossible in the dangerous direction, plus `scripts/assert-authz-projection.mjs` in CI.
- **Cedar's transitive `in` widens project-scoped grants beyond station's current semantics** — a project grant will reach Runs/Gates/Artifacts under that Project, which station's literal `:projectId` matching does not do today. This is intended and better, but it is a behaviour change on a security boundary. Mitigation: Phase 1 shadow mode will report it as a divergence class; it must be reviewed and explicitly accepted (with a test) rather than dismissed as noise.
- **TypeORM 1.1.0's `engines.node` is `^20.19 || ^22.13 || >=24.11`, but the @nestm family requires `>=22.12`.** A consumer on exactly Node 22.12 gets a peer/engine warning. Low severity; mitigation is to document `>=22.13` for the TypeORM driver specifically, or relax the family floor for that one package.
- **`defineVocabulary` eagerly loading WASM (core as written) would pull ~4.1 MiB into `packages/platform`,** which `packages/web` transitively reaches — a real bundle regression in station's console. Mitigation is core delta D3 (lazy validation); if core declines, station must put the vocabulary in `apps/api` instead and lose the framework-free placement.
- **Plan cache keying is security-sensitive.** Core's key includes `hash(principalAncestorUids)`, so a stale principal-ancestor set (e.g. a grant revoked but the entity cache not invalidated) yields a stale plan that over-shares. Mitigation: the driver's `PolicyChangeEvent` for a scope must invalidate the entity cache for that scope too, not just the policy set — assert this in the store conformance suite.
