# Design errata — live-verified corrections to `docs/design/*.md`

Corrections discovered during implementation, each verified against real `cedar-wasm@4.12.0`. The design docs are kept as written; this file is authoritative where they conflict.

## core.md

1. **§0 evict-by-empty (slice 2b):** `preparsePolicySet(id, { staticPolicies: {} })` frees the slot's memory but leaves the id **registered** — a subsequent `statefulIsAuthorized` against the evicted id returns `{type:"success", decision:"deny"}` (fail-closed), **not** the "preparsed policy set … not found" failure. The "not found" failure occurs only for ids never preparsed. Consequence: eviction is safe (deny, never allow), but "id not found" cannot be used to detect eviction.
2. **§2 `defineVocabulary` eager `checkParseSchema` (slice 2a):** overridden by plan delta D3 — the builder is pure TS; Cedar validation happens on demand via `validateVocabulary`/`assertVocabularyValid` and at engine creation. `Vocabulary.toCedarSchemaText` takes an explicit `CedarBinding` parameter.
3. **§6 `CedarBinding` (slice 2b):** `templateToText` added to the interface — `policyToText` rejects template JSON ("expected a static policy, got a template"), so template text round-trips require the dedicated function.
4. **Action groups (slice 2a):** modeled Cedar-natively — an `actions` entry with neither `principal` nor `resource` is a group. Cedar rejects authorization requests naming a group directly (verified), so `ActionOf<V>` excludes groups; `ActionGroupOf<V>` names them.
5. **`buildPolicySet` (slice 2b):** takes optional `{ namespace }` second argument — template-link values hold vocabulary-local entity types that must be namespace-qualified for Cedar.
6. **§1 `EngineOptions.clock` (slice 2c):** typed `() => number` (milliseconds), not `() => Date`. The engine hands its clock straight to `PolicySetCache`, which shipped in slice 2b with `clock?: () => number` because every use is a delta (`preparedAt` vs `staleAfterMs`); `CheckResult.durationMs` is the same kind of delta. A `Date`-returning seam would allocate two `Date`s per 0.136 ms check purely to be subtracted. Default is `Date.now`, whose 1 ms resolution rounds a typical check to `0` — pass `() => performance.now()` when `durationMs` must be meaningful.
7. **§0/§7 `validateOnLoad` is stricter than "unknown entity type" (slice 2c):** verified against 4.12.0, `validate()` reports **unguarded access to an *optional* attribute** as a `validationError`, not a warning — `when { context.mfa == true }` on an optional `mfa` is rejected, and must be written `when { context has mfa && context.mfa == true }`. Consequence: `validateOnLoad: true` (the default) refuses policy sets that Cedar's *parser* accepts and that evaluate fine most of the time, which is the intended behaviour — the unguarded form is exactly the shape that makes a `forbid` error and vanish (§0 finding 21). Also verified: `preparsePolicySet` succeeds on a policy referencing an undeclared entity type, so `validate()` is a genuinely separate gate rather than a redundant one.
## nestjs-module.md (slice 3a adaptations to the shipped core)

1. **§3 options**: `schema: CedarSchemaSource` → `vocabulary: AnyVocabulary`; the `PERMISSIONS_SCHEMA` token is dropped (vocabulary reachable via options token and `engine.vocabulary`).
2. **§3 two-phase init → single lazy phase**: core's `PolicySetCache` loads per scope on first check, so the `'unloaded'|'ready'|'stale'` state machine has no counterpart. `PolicySetManager` warms `warmScopes` at `OnModuleInit` (failures logged, not fatal — lazy per-request retry is the core semantic), owns `reload()` (= `engine.invalidate('*')`), `revision(scope)` (= `store.currentVersion`, async), `assertReady()` (fails only on a disposed engine → 503), and `OnApplicationShutdown` dispose.
3. **Seeds (`policies`/`links`) are only for the built-in memory store** — combining `store` with seeds throws in `forRoot` (never issue unrequested `save()`s against a caller's database). Text seeds parse inside the async store factory (needs the Cedar binding); `forRoot` stays sync and WASM-free.
4. **Store/resolver definition unions resolve at runtime via `ModuleRef`**, not static module metadata (forRootAsync produces options after the graph exists).
5. **`checkAll` → `checkMany`** (core's name); `PermissionsService.plan()` deferred to the guard slice; `stats()` added.
6. **Two `onDecision` hooks by design**: `engine.onDecision` (core per-check listener, fires for imperative calls) and `hooks.onDecision` (route-level, consumed by the guard).
7. **`ActionOf<AnyVocabulary>` is `never`** (open def optionality), so `ActionName`/`ResourceTypeName` use `[X] extends [never] ? string : X` for the unaugmented-registry fallback.
8. **`EntityProvider` naming**: the decorator owns the bare name; core's interface re-exported as `CoreEntityProvider`; feature classes implement `FeatureEntityProvider` (all methods optional). `@EntityProvider({ order })` supported; empty registry surfaces core's `ENTITY_RESOLUTION` error rather than masking it.
9. **`instanceId` uniqueness** enforced at engine creation and released on shutdown/failure (`internal/instance-registry.ts`) — registration-time checking would break boot/close/boot.

## nestjs-module.md (slice 3b — the guard, decorators, denial strategy, audit)

1. **§4 `parseAs` drops the `"uuid" | "int" | "string"` shorthands** — Standard Schema only. A built-in half-validator invites exactly the divergence `parseAs` exists to prevent: the guard would accept an id the handler's real schema rejects, or vice versa. The spec is structural and dependency-free, so the twenty-line hand-written validator in `examples/station-fastify/src/runs/run-id.schema.ts` is the whole cost of not having them.
2. **§4 an omitted `resource` is not "no check"** — it infers `{ kind: 'unspecified', type }` from the action's single declared resource type and takes the **query-plan** path; an action declaring zero or several resource types is a configuration error naming both. The guard warns once per route, because allowing then only means *some* row is reachable and the handler must apply the plan.
3. **§5 `Denial` union extended** and renamed `PermissionsDenial`: `forbidden` carries the `CheckResult` (core exposes no `AuthorizationDiagnostics`), and four arms are added — `not-in-scope` (the resolver's `NOT_IN_SCOPE`, distinct from the gate's `not-a-member` for audit purposes but **identical in response**), `plan-denied`, `undeclared-route`, `misconfigured`. `denial.onInvalidParam` is a `DenialOptions` member taking an `InvalidParamContext`, not a hook.
4. **§4 scope resolution was unspecified; it is now `scopeFrom` + `scopeResolver`.** The guard needs the scope *before* the principal (the resolver is told which scope it is being asked about), so the order is: route `scopeFrom` (`literal` | `param` with `prefix` | `resolver`) → module `scopeResolver` → the principal's `scopeHint` → the global scope. `scopeHint` is **last** deliberately: when the URL names one tenant and the principal claims another, honouring the principal is a cross-tenant read.
5. **The 404 body is a frozen constant** (`NOT_FOUND_DETAIL`), and `createAuthorizationError` **ignores** the `message` argument for `NOT_FOUND`. Byte-identity between an unknown tenant and a non-member probe is a property no call site should be able to break by passing a helpful message.
6. **§6 `PATH_METADATA` is loaded asynchronously**, not via `createRequire`: `@nestjs/common@12` is ESM. `loadRouteMetadataKeys(load?)` memoises, takes an injectable loader, and falls back to the literals `'path'`/`'method'` — which is what Nest actually writes, so an audit on the fallback identifies the same routes.
7. **`AnyFeatureEntityProvider` (new).** `FeatureEntityProvider<A>` and `FeatureEntityProvider<B>` are genuinely unrelated — `EntityResolutionRequest<V>` reaches `ActionOf<V>` and thence the vocabulary's `namespace` literal, so neither assignment direction holds and method bivariance does not rescue it. Invisible until an application augments `PermissionsTypeRegistry`, at which point the registry would refuse every provider in the application. The registry therefore stores providers under a variance-free interface whose parameter is `never` in *property* position, with one documented cast at the single call site. **Found by the example app's typecheck, not by the package's own tests** — nothing in-package augments the registry.
8. **`QueryPlan` is exported from `decorators/authorization.decorator.ts`**, which declares both the parameter decorator (a value) and a re-export of core's plan type. One export specifier carrying two declaration spaces; two barrel re-exports of the same name would be a duplicate export.
9. **`RouteResolutionContext.action` is `ActionName | undefined`** — a `@RequireAuthenticated()` route has a scope and a principal but no action. `ResourceResolutionContext` narrows it back to `ActionName`, since a resource is only ever resolved for a declared action.
10. **Entities are always passed explicitly**, never left to the engine's provider path: `entityGraph(...principal.entities, ...registry.resolveRouteEntities(...))`, deduplicated because Cedar rejects a slice listing one UID twice and principal/resource graphs routinely share an ancestor. With no `@EntityProvider()` registered and a resource absent from the principal graph, the guard warns once per route and the decision fails closed.

## core.md (continued)

8. **§4 entity tags (slice 2c):** cedar-wasm rejects an entity carrying a tag the schema does not declare (`error during entity deserialization: found a tag ... but no tags should exist ... according to the schema`), and the schema only reaches the call when `validateRequests` is on. `defineVocabulary` does not model tags, so `entity(..., { tags })` is usable only with `validateRequests: false` or a hand-extended schema. Tag support in the vocabulary builder is unscheduled.
9. **§5.6 plan cache key is insufficient as specified (slice 4a):** the key is documented as `sha256(instanceId, scope, policySetVersion, principalUid, hash(principalAncestorUids), action, resourceType, canonicalJson(context), vocabHash)`. Ancestor uids alone are **not** enough. Verified: `permit(..., resource) when { resource.project in principal.organization }` produces the residual `{"in":{"left":{".":{"left":unknown,"attr":"project"}},"right":{"Value":{"__entity":{"type":"Station::Organization","id":"o1"}}}}}` — the principal *attribute* is folded into a literal in the compiled filter. Two principals with identical ancestors and different attributes would therefore share a plan and one would receive the other's filter. The implementation hashes the **whole resolved entity graph**, canonicalised order-independently (entities sorted by uid, parents sorted, attribute records through `stableStringify`), which subsumes the ancestor set and is strictly safer.
10. **§5.2 `PlanValue` is missing two variants (slice 4a):** §5.4 requires `decimal` and `ipaddr` constants on the non-unknown side, but §5.2's `PlanValue` union lists neither. Verified shapes: `{"decimal":[{"Value":"1.5"}]}` and `{"ip":[{"Value":"10.0.0.0/8"}]}`. Both are carried as the **Cedar literal text** (`{kind:'decimal', value:'1.5'}` / `{kind:'ipaddr', value:'10.0.0.0/8'}`) — neither has a lossless JavaScript representation and a driver binds them to `NUMERIC`/`INET` as text anyway.
11. **§5.2 `long` precision is already lost before this package sees it (slice 4a):** `PlanValue.long` carries a `bigint`, but the residual crosses the WASM boundary as JSON. Verified: `resource.attempt == 9007199254740993` comes back as `{"Value":9007199254740992}`, and `-9223372036854775808` as `{"Value":-9223372036854776000}`. The `bigint` keeps the *driver* side exact; it cannot undo the rounding. Longs outside ±2^53 are not representable through a query plan.
12. **§5.4 pushdown table is missing two residual shapes cedar actually emits (slice 4a):**
    - a **bare boolean attribute** at boolean position — `when { resource.archived }` yields the residual `{".":{"left":unknown,"attr":"archived"}}` with no comparison wrapper. Compiled as `cmp eq` against `{kind:'bool', value:true}`, which is exact (Cedar's validator rejects a non-Bool there, and a mistyped one lands in `errored[]`).
    - **row identity** — `permit(..., resource == Station::Run::"r1")` does *not* stay in the residual's `resource` constraint; like every other scope constraint it flattens to `{op:"All"}` and reappears in `conditions` as `{"==":{"left":unknown,"right":{"Value":{"__entity":…}}}}`. No `PlanNode` expresses "the row itself equals this entity" (`inHierarchy` is Cedar's reflexive-and-transitive `in`, which is strictly wider, so mapping `==` onto it would widen a permit). It is **rejected**, with reason `entity-identity`.
13. **§5.4 `resource is T in P` decomposes before the compiler sees it (slice 4a):** verified, Cedar emits `{"&&":{"left":{"is":…},"right":{"in":…}}}` rather than the `{"is":{left, entity_type, in}}` arm its own `.d.ts` declares. Both are handled; only the decomposed form occurs in practice.
14. **§5.1 `QueryPlan` arms (slice 4a, deviation):** `resourceType` and `approximations` are carried on **every** arm, not only on `CONDITIONAL`. An `ALWAYS_DENY` produced by `onErroredPolicy: 'deny-all'` genuinely carries approximations, and a driver's `planToSql(plan, mapping)` wants to assert the mapping matches the type on all three arms. Related: a plan that needs a post-filter and whose condition simplifies to `true` stays **`CONDITIONAL` with `condition: {op:'true'}`** rather than collapsing to `ALWAYS_ALLOW` — `ALWAYS_ALLOW` has no `postFilter` field, so collapsing would silently drop the only thing making the widened plan sound.
15. **§5.5 `PlanApproximation['reason']` union extended (slice 4a):** core.md lists seven members; four more are produced because they are distinguishable and actionable — `unsupported-operator` (`containsAll`/`containsAny`/`getTag`/`hasTag`/bare `Var`/`Slot`), `unsupported-value` (record literal, unparseable extension literal, non-integer `Value`), `non-literal-hierarchy` (`in` whose right side is not one concrete entity), and `entity-identity` (erratum 12). `unmapped-hierarchy` is retained but never produced here — it is reserved for the ORM drivers.
16. **§5.3 partial evaluation needs the built `PolicySet` in JS (slice 4a):** confirmed against the shipped `.d.ts` — `PartialAuthorizationCall` has `policies: PolicySet` and **no** `preparsedPolicySetId`. `PolicySetCache` therefore retains the compiled `PolicySet` on its LRU entry (`policySetFor(scope)`), released by the same `onEvict`/`dispose` path as the WASM id. Retention costs no extra work (the object is built on the load path regardless) and is bounded by the same `maxScopes` the operator already tunes for WASM memory; the alternative — `store.load` + `buildPolicySet` per `plan()` — is a database round-trip on the plan hot path, defeats D1 and makes the plan cache pointless.
17. **§0 errored policies can also arrive with a *determined* decision (slice 4a):** verified — an unguarded `context.mfa` in a forbid gives `{decision:"deny", errored:["f1"], nontrivialResiduals:[]}`, and with a residual permit alongside it gives `{decision:null, errored:["f1"], nontrivialResiduals:["p1"]}` with the forbid's residual reduced to `{"Value":false}`. The `errored[]` gate must therefore run **before** the `decision` short-circuit, or an errored forbid would be invisible on every determined request.
18. **§5.2 `decimal` is not orderable by Cedar's `<`/`<=` (slice 4b):** `plan-node.ts`'s `ORDERABLE_KINDS` lists `decimal`, but verified against 4.12.0 `decimal("1.5") < decimal("1.5001")` is a **type error** — `expected one of [long, datetime, duration], got decimal`. Cedar orders decimals only through the extension calls `lessThan`/`lessThanOrEqual`, which are extension calls *applied to the unknown* and therefore rejected by the compiler as `extension-on-unknown`. A `cmp lt` node carrying a `decimal` is consequently unreachable from `plan()`. `assertOrderable` is left accepting it: the guard exists to stop a driver emitting `<` for a kind SQL would order differently from Cedar (strings under a collation, entities, sets), and permitting an unreachable-but-numerically-sane kind is not a soundness hole. `evaluatePlanNode` implements decimal ordering at Cedar's fixed 4-digit precision for the same reason.
19. **§5.7 `evaluatePlanNode` is three-valued, not two-valued (slice 4b, deviation):** the signature in §5.7 returns `boolean`, and it does — but internally a leaf that reads an attribute the row does not have evaluates to UNKNOWN and propagates by Kleene's rules before collapsing to `false` at the top. This is required for the interpreter to be a valid oracle for a SQL driver: `NOT(col = 'x')` over a NULL column is NULL in SQL (row dropped), whereas two-valued logic would return `true` and select it. Under the `has`-guarded shape `validateOnLoad` enforces, Cedar, this interpreter and SQL all agree, because `false AND UNKNOWN` is `false` in all three. `null` and `undefined` and an absent key are all "absent" — `null` is what a driver reads back from a nullable column.
20. **§5.7 `HierarchyResolver` receives more than `{attr, rowId, parent}` (slice 4b):** the query object also carries `row` and `value` (`row[attr]`). A resolver destructuring only the three documented fields still type-checks, so this is additive; without it a resolver could not answer `resource.folder in Folder::"f1"` at all, since the attribute's value lives in the row and nowhere else.
21. **Cedar `ipaddr` equality compares the address and prefix, not the network (slice 4b):** verified — `ip("1.2.3.4") == ip("1.2.3.4/32")` → true (a bare address is a full-width prefix); `ip("::1") == ip("0:0:0:0:0:0:0:1") == ip("::0001")` and `ip("FE80::1") == ip("fe80::1")` → true (zero-compression and hex case are not significant); but `ip("1.2.3.0/24") == ip("1.2.3.1/24")` → **false** and `ip("1.2.3.0/24") == ip("1.2.3.0/25")` → **false**. Also verified rejected at evaluation: `ip("01.2.3.4")` (leading zeros) and `ip("::ffff:1.2.3.4")` (IPv4-mapped). `evaluatePlanNode` normalises to `(family, address bytes, prefix length)` and rejects the two forms Cedar rejects; exact-text matching would have been wrong on five of those nine cases.
22. **Cedar has no `\%` escape in a `like` pattern (slice 4b):** `like "50\%*"` is a **parse** error — "the input `\%` is not a valid escape". Only `\*` (and the ordinary string escapes `\\`, `\"`) are valid. `%` and `_` are ordinary characters to Cedar and metacharacters to SQL, which is the exact asymmetry `LikeToken` exists to carry; a policy author porting a SQL pattern will write `\%` and get a compile error rather than a silent wildcard, which is the right failure.
23. **Cedar sets are unordered and duplicate-insensitive (slice 4b):** verified — `[1,2,2] == [2,1]` is `allow`. `evaluatePlanNode` compares `set` values by mutual containment rather than element-wise, and a driver storing a set as an array column must do the same.
24. **§5.2/§5.4 corpus longs outside ±2^53 cannot cross the JSON boundary at all (slice 4b, extends erratum 11):** erratum 11 records that such longs are *rounded*. Stronger, from the Cedar corpus runner: an entity or context carrying `9223372036854775807` makes cedar-wasm **reject the whole call** — `data did not match any variant of untagged enum RawCedarValueJson` (surfacing as `error during entity deserialization: …` for entities). Passing a `BigInt` instead throws out of serde-wasm-bindgen (`called Result::unwrap_throw() on an Err value`). 84 of the 7600 auto-generated corpus cases are affected and are skipped by a pre-flight unsafe-integer scan; with them excluded the remaining 60 128 requests match Cedar's expected decision **and** determining-policy set exactly.

## drivers-and-station.md (slice 7 — the Drizzle driver's test suites)

1. **§3 `jsonPath` mappings needed `sql.param` (found by the golden-SQL suite):** the design's AST→SQL table gives the jsonb spellings but not how the *path* is bound. A bare array interpolated into drizzle's `sql` template is spread into one placeholder **per element**, so `sql`${col} #>> ${['tier']}`` renders `#>> ($1)` — which Postgres reads as a scalar and rejects with `malformed array literal: "tier"` — and a depth-2 path renders `#>> ($1, $2)`, a row constructor. Verified against `drizzle-orm@0.45.2` and Postgres 16. Every `jsonPath` attribute (`cmp`, `in`, `contains`, `exists`, `isEmpty`) was affected; none was reachable from the differential suite, whose fixture has no `jsonb` column. Fixed by wrapping the path in `sql.param([...path])`, which keeps it a single `text[]` parameter that node-postgres serialises as `{tier}`. Consequence for the TypeORM mirror: the same trap exists wherever a path array is passed to a query builder that flattens arrays into parameter lists — bind the path as one array parameter, and make the golden suite *execute* its statements rather than only compare their text.
2. **Verified: Postgres `inet` equality agrees with Cedar's `ipaddr` equality on every case in core erratum 21 (slice 7):** all seven comparison pairs were re-run against Postgres 16 and match Cedar exactly — `1.2.3.4 = 1.2.3.4/32` **true**; `::1 = 0:0:0:0:0:0:0:1` and `::1 = ::0001` and `FE80::1 = fe80::1` **true**; `1.2.3.0/24 = 1.2.3.1/24` **false**; `1.2.3.0/24 = 1.2.3.0/25` **false**; `10.0.0.1 = 10.0.0.2` **false**. So binding a `PlanValue.ipaddr` as its Cedar literal text with `::inet` reproduces Cedar's semantics; the two tempting alternatives do not — `::text` equality is wrong on the **four** pairs Cedar calls equal but spells differently, and `<<=` (network containment) is wrong on `1.2.3.0/24` vs `1.2.3.1/24`, which it calls true and Cedar calls false. One divergence exists and is on the *column* side, not the compiler's: Postgres **accepts** `01.2.3.4` (normalising it to `1.2.3.4`) and `::ffff:1.2.3.4`, both of which Cedar rejects at evaluation. A `PlanValue.ipaddr` can never carry either — it comes from a literal Cedar already parsed — but a row whose `inet` column holds one is a row Cedar would have errored on, so it is a data-modelling caveat for the consumer rather than a compiler bug. Pinned by `tests/integration/value-binding.test.ts`.
3. **`ALTER TABLE … FORCE ROW LEVEL SECURITY` does not apply to a superuser (slice 7):** the RLS harness therefore cannot assert isolation as the owning/connecting superuser — `BYPASSRLS` is implicit for superusers regardless of `FORCE`. The harness creates a dedicated `NOLOGIN NOBYPASSRLS` role and runs its assertions under `SET LOCAL ROLE`, which is what station's `station_app` is. A harness that skipped the role switch would report green against a table with no working policy at all.
4. **§2 the store must not issue overlapping queries (slice 7, found by the RLS harness):** `DrizzlePolicyStore.load()` originally read policies, links and versions with one `Promise.all`. That is correct and one round trip against a *pool* — and against a `transaction()` handle it emits `Calling client.query() when the client is already executing a query is deprecated and will be removed in pg@9.0`. A transaction handle is a single `pg` client. This matters because running the store over a transaction is not an exotic call shape under RLS but the **required** one: `set_config('station.organization_id', …, true)` is transaction-local, so a store issuing its statements on a different pooled connection sees no tenant context and reads zero rows. `load()` is a cold path (D1 — the engine caches per scope and `watch()` invalidates), so the three reads are now sequential and the two extra round trips are the cheap side of the trade. Pinned by `tests/integration/rls.test.ts > issues no overlapping queries when run over a transaction handle`. The TypeORM mirror has the same constraint wherever it fans out reads over an `EntityManager` taken from a transaction.
5. **§1 the design's `USING`/`WITH CHECK` predicate is exactly right, and the empty string matters (slice 7):** `nullif(current_setting('station.organization_id', true), '')::uuid` yields NULL when unset, `col = NULL` is NULL, and the row is excluded — so an unset context reads **zero** rows rather than raising. Verified that a context set to `''` behaves identically to an unset one, and that a write naming another tenant is refused by `WITH CHECK` with SQLSTATE `42501`. Note for anyone reading a failure: drizzle wraps the driver error in its own `Failed query: …`, so the `new row violates row-level security policy` text is on `error.cause`, not on the thrown error's own message.

## drivers-and-station.md (slice 5 — the TypeORM driver)

1. **§1/§5 TypeORM cannot express the `GIN (cedar_json jsonb_path_ops)` index, and actively fights a hand-added one.** `EntitySchemaIndexOptions` has no `using` member (verified against `typeorm@1.1.0`), so tier 1 (`migration:generate`) can only emit a **btree** index over a `jsonb` column — syntactically fine, useless for `@>`, and silent about it. `createPermissionsEntities` therefore omits the index and `permissionsPostgresIndexStatements()` hands consumers the statement; `buildPermissionsMigration`/`PermissionsInitialMigration` include it. The sharper half, also verified: TypeORM's schema builder does not merely *ignore* an index it did not declare — it proposes `DROP INDEX` for it on every subsequent generate, because "the entity is the truth" is the premise of `migration:generate`. So on tier 1 the index and the generator are in a standoff, which is pinned by an assertion (`tests/integration/migrations.test.ts`) rather than discovered by a consumer. The Drizzle driver has the index natively, so this is the one physical-schema difference between the two drivers, and only on tier 1.
2. **§3 `planToBrackets` compiles twice, on purpose.** The final SQL needs two things only the *target* query builder has: its main alias and the parameter names already on it, both available solely inside the `Brackets` factory. A mapping error discovered there would surface halfway through `getQuery()`, from a frame the caller never wrote. So the expression is compiled eagerly with a placeholder alias purely so every fail-closed check fires at the call site, then again inside the factory to produce the text that runs. Compilation is a pure walk over a small AST; the alternative is a library whose errors arrive at the wrong time and whose failed `applyPlan` leaves a half-filtered builder behind.
3. **§3 `applyPlan` appends in TypeORM and replaces in Drizzle.** `qb.andWhere()` composes; drizzle's `.where()` overwrites. The design's table does not distinguish them, and the compiled predicate is identical — but the *sugar* cannot be, because a TypeORM helper that replaced would be discarding whatever the caller had already put on the builder, and a drizzle helper that claimed to append would be lying. Documented in both READMEs.
4. **§2 `load()`'s reads must be sequential, not `Promise.all`.** Two independent reasons, and the second is the one that bites: a pooled `EntityManager` hands three concurrent reads three *different* connections, so the three halves of a bundle can straddle a concurrent write (policies from before, links from after, version from either) — a bundle assembled from two points in time, which `buildPolicySet` cannot detect and the cache will keep. And an `EntityManager` bound to a query runner (any RLS deployment wrapping the store in its own `set_config` transaction) has exactly one client, on which overlapping queries are removed in `pg@9`. Three sequential round-trips on the cold-load path cost a fraction of a millisecond each.
5. **§1 the `scope_versions` RLS carve-out has a nameable cost, not just a rationale.** With no RLS on that table, one tenant *can* read another tenant's revision counter. That is the entirety of what leaks — an integer meaning "something changed", keyed by a tenant id the application already knows — and it is asserted as such (`tests/integration/rls.test.ts`, "exposes only a counter across tenants") rather than left as a paragraph a reviewer has to reconstruct. The policy tables themselves stay invisible without a context, which is the half that matters.
6. **§5 `engines.node` for the TypeORM driver is `>=22.13`, not the family's `>=22.12`.** `typeorm@1.1.0` declares `^20.19 || ^22.13 || >=24.11`; on 22.12 the peer resolves and then warns at runtime. Raising the package's own floor turns that into a resolution error at install time.

## Station migration — risk burn-down (multi-resource-type role templates)

1. **A single Cedar template may name actions whose declared resource types differ, and `validate()` accepts it with no error and no warning.** Verified against `cedar-wasm@4.12.0`; pinned by `packages/permissions-core/tests/integration/multi-resource-template.test.ts`. The station shape

   ```cedar
   permit(principal == ?principal,
          action in [Station::Action::"project:manage",
                     Station::Action::"run:read",
                     Station::Action::"run:dispatch"],
          resource in ?resource);
   ```

   where `project:manage` declares `resource: Project` and the two `run:*` actions declare `resource: Run`, validates **clean** — `{ type: "success", validationErrors: [], validationWarnings: [], otherWarnings: [] }`, byte for byte. The same holds for an unconstrained `resource` scope and for `resource == ?resource`, and at station's real width: a generated case with **25 actions across 5 declared resource types** (`Organization`/`Project`/`Run`/`Secret`/`Webhook` × 5 verbs) also validates clean, links included. **Verdict: the staged migration's one-template-per-role design survives. It does not have to split per resource type.**

2. **Template *links* to such a template evaluate correctly for every named action, including actions whose declared resource type is unrelated to the linked `?resource`.** With one link at `?resource = Station::Organization::"o1"` — an entity type no named action declares as a resource at all — both `run:dispatch` on `Run::"r1"` and `project:manage` on `Project::"p1"` are **allowed**, with the link id as the sole determining policy, under `validateOnLoad: true` and under `validateRequests` in **both** settings. Cedar resolves `Run::"r1" in Organization::"o1"` through the entity graph; the scope constraint is a hierarchy test, not a type test. Splitting the same grant into one template per resource type produces identical decisions and differs only in which link id is reported as determining — so the one-template form costs nothing observable and saves N−1 rows per grant.

3. **Three real constraints come with it, and all three are the same constraint stated three ways: the *scope* of such a template is permissive, so nothing about a specific resource type may leak into it.**
   - **A `when` clause over an attribute only some of the named resource types declare is a `validationError`.** `… resource in ?resource) when { resource.status == "queued" }` over the three-action template is rejected with `for policy \`role:member\`, attribute \`status\` on entity type \`Station::Project\` not found` (plus `did you mean \`archived\`?`). The condition is typechecked against the **union** of every named action's declared resource type, so a multi-resource-type role template must carry **no** resource-attribute condition. A role that needs one needs its own, narrower template.
   - **A link whose `?resource` makes *every* named action unreachable is rejected** — `unable to find an applicable action given the policy scope constraints`, reported against the **link's** id, not the template's. One reachable action is enough to pass, so a link at `?resource = Run::"r1"` validates even though `project:manage` can never fire under it (a Project is never `in` a Run).
   - **`validateRequests` is the only thing that stops a schema-invalid action/resource pairing being *allowed*.** With `validateRequests: false`, `checkUnsafe({ action: "project:manage", resource: Run::"r1" })` under the org-wide link returns **allow**: the permissive scope matches and Cedar never consults the schema. With `validateRequests: true` (the default) the same call throws `resource type \`Station::Run\` is not valid for \`Station::Action::"project:manage"\``. Consequence for station: the one-template-per-role design is safe **because** `validateRequests` is on, and turning it off would convert every one of these templates from "25 actions, each on its own resource type" into "25 actions on any resource type in the org". That is a boot-time setting guarding a data-shape assumption, which is worth naming in the runbook rather than leaving to the default.

## drivers-and-station.md (station-readiness pass — the Drizzle schema factory)

1. **§4e and the driver README were wrong about the scope column's key: it is `scope`, never the SQL name.** `createPermissionsSchema`'s column map keys the tenant column by the drizzle **property** name `scope` on all three tables; `scopeColumn.name` sets only the SQL name. So `extraTableConfig` must read `t.policies.scope` even when the column is `organization_id`. The failure is silent rather than loud: `t.policies.organizationId` is `undefined`, and a `pgPolicy` built by interpolating it into a `sql` template is a policy over nothing. Fixed in the README; pinned by `packages/permissions-drizzle/tests/unit/schema-factory.test.ts > the scope column's property name`.
2. **`extraTableConfig` was invoked once per table, and the guarded workaround that fact forced was worse than the crash it avoided.** `pgTable()` does not call its config callback — it stores it, and drizzle-kit calls each table's independently and in **no guaranteed order**. Resolving `extraTableConfig` from inside those callbacks therefore evaluated the consumer's whole returned object once per table, each time against a differently-filled `tables`. Two failure modes, verified against `drizzle-orm@0.45.2`: an entry dereferencing a table not yet built threw `TypeError: Cannot read properties of undefined (reading 'scope')` from inside drizzle-kit, naming neither the option nor the table; and guarding the branches (`tables.policies === undefined ? [] : […]`, which is what the staged station artifact does) traded that crash for a **silent omission** — a `links` entry guarded on `tables.policies` produced `[]` whenever the links table was serialised first, so its composite foreign key and its RLS policy were simply absent from the migration, with no error anywhere. The factory now primes all three config callbacks itself at construction, then resolves `extraTableConfig` exactly once with every table populated, memoised per key. Existing guarded implementations keep working and now always take the populated branch.
